# Phase 14 — Patient Documents & Secure Storage

## 1. Phase Objective

Build a secure, production-quality **Patient Documents & Secure Storage** system for Punarvasu.

The system should allow authorized users to upload, store, retrieve, preview, download, and manage patient-related documents while maintaining strict privacy and access control.

Potential document types include:

* laboratory reports
* diagnostic reports
* medical images
* previous prescriptions
* treatment-related documents
* referral documents
* consultation-related attachments
* patient-uploaded supporting documents

The exact document categories must remain configurable and should not assume a fixed medical workflow without verified requirements.

This phase introduces another category of highly sensitive patient data.

Security and privacy are therefore first-class requirements.

---

# 2. Critical Security Principle

Documents must be treated as private healthcare data.

The application must never rely on:

```text
"Only show the download button to authorized users."
```

as the security mechanism.

Instead:

```text
Authenticated User
        ↓
Application Authorization
        ↓
Resource Ownership / Care Relationship
        ↓
Storage Authorization
        ↓
Private File Access
```

The browser UI is not a security boundary.

# 4. Storage Architecture

Use Supabase Storage according to the project's established Supabase architecture.

The preferred conceptual structure is:

```text
Private Storage Bucket
        ↓
Object
        ↓
Document Metadata
        ↓
Patient / Clinical Relationship
        ↓
Authorization
```

Do not expose the bucket publicly.

---

# 5. Private Bucket

Healthcare documents must be stored in a **private bucket**.

Do not use:

```text
public = true
```

for patient documents.

Do not expose permanent public URLs.

---

Use a database table such as:

```text

```

The exact fields must follow the existing architecture and actual requirements.

---

# 7. Database as Source of Truth

The database should store metadata and authorization relationships.

Storage should contain the actual file.

Conceptually:

```text
Database
    ↓
patient_documents
    ↓
storage_path
    ↓
Supabase Storage object
```

Do not attempt to store binary files directly in PostgreSQL unless there is a specific requirement.

---

# 8. Storage Path Design

Do not use arbitrary user-controlled paths.

Avoid:

```text
uploads/${file.name}
```

or:

```text
${file.name}
```

Prefer a controlled namespace such as:

```text
patients/{patientId}/documents/{documentId}/{safeFileName}
```

or an equivalent secure structure.

The final path should be generated by the server/application.

---

# 9. File Name Security

Never trust the original filename as the storage object key.

A filename such as:

```text
../../sensitive-file.pdf
```

must not be able to manipulate storage paths.

Generate safe object names/IDs.

Preserve the original filename only as metadata where useful.

---

# 10. Supported File Types

The system should define an explicit allowlist.

Potential formats:

```text
PDF
JPEG
PNG
WEBP
HEIC
```

depending on actual requirements.

Do not allow arbitrary executable or dangerous formats.

Potentially dangerous types such as:

```text
.exe
.sh
.bat
.js
.html
.svg
```

must be carefully handled or rejected.

Do not trust MIME type supplied by the browser.

---

# 11. MIME Type Validation

Client-side validation is useful for UX but insufficient.

The server must validate:

```text
declared MIME type
file extension
file signature / content where practical
```

Do not rely only on:

```ts
file.type
```

from the browser.

---

# 12. File Size Limits

Define reasonable upload limits.

For example:

```text
Maximum file size = configurable
```

Do not hard-code a random value without considering:

* Supabase limits
* deployment limits
* clinic requirements
* expected report sizes
* mobile uploads

The limit should be centralized in configuration.

---

# 13. Upload Validation

Before accepting a document:

```text
Authenticate
→ Authorize
→ Validate patient relationship
→ Validate document metadata
→ Validate file size
→ Validate file type
→ Generate secure storage path
→ Upload
→ Create metadata
```

---

# 14. Upload Atomicity

Avoid creating orphan metadata or orphan files.

Bad:

```text
Create DB row
→ Upload fails
→ DB points to nonexistent file
```

Also avoid:

```text
Upload succeeds
→ DB insert fails
→ inaccessible orphan object remains
```

Where practical, implement compensation/cleanup logic.

```text
Upload
      ↓
Server Validation
      ↓

      ↓
Metadata Record
      ↓

```

The exact implementation can use a signed upload workflow if appropriate.

---

# 16. Who Can Upload?

The permission model must explicitly define upload permissions.

Potentially:

### Patient

Can upload documents belonging to themselves.

### Doctor

Can upload documents for an authorized patient/care relationship.

### Receptionist

Should generally NOT upload clinical documents unless explicitly required.

### Admin

Does not automatically receive clinical document access.

Do not infer permissions simply from authentication.

---

# 17. Patient Ownership

A patient upload must always resolve to the authenticated patient's own profile.

Never trust:

```json
{
  "patientId": "another-patient"
}
```

from the browser.

---

# 18. Doctor Upload

If doctors can upload documents:

```text
Authenticated doctor
        ↓
Resolve practitioner
        ↓
Verify patient/care relationship
        ↓
Verify appointment/clinical context where required
        ↓
Upload
```

A doctor must not be able to upload arbitrary files into another doctor's unrelated patient.

---

# 19. Receptionist Access

Receptionists should not automatically receive access to sensitive documents.

If the clinic later requires operational document handling, create a narrowly scoped permission.

Do not grant:

```text
documents.read.all
```

just because the user is a receptionist.

---

# 20. Admin Access

Admin role does not automatically imply clinical document access.

Administrative access should be explicitly permissioned and auditable.

```text

Authorized doctor → documents for authorized patients

```

# 30. Secure Downloads

Do not expose permanent public URLs.

Prefer:

```text
Authorized request
      ↓
Server checks permission
      ↓
Generate short-lived signed URL
      ↓
Browser downloads/opens
```

or an equivalent secure server-mediated approach.

Signed URLs should expire.

---

# 31. Signed URL Security

Never generate a signed URL before authorization.

Bad:

```text
GET /documents/:id/url
→ immediately generate signed URL
```

Good:

```text
GET /documents/:id/url
→ authenticate
→ authorize
→ generate short-lived URL
```

---

# 32. URL Expiration

Signed URLs should have a short, reasonable lifetime.

Do not create long-lived links such as:

```text
expires in 30 days
```

unless a specific workflow requires it.

---

# 33. No Permanent Download Links

Do not put:

```text
https://storage.../public/...
```

into database records or patient pages.

Store object paths, not permanent public URLs.

---

# 34. Document Deletion

Deletion of healthcare documents is sensitive.

Do not implement unrestricted delete.

Potential policy:

```text
Patient → cannot delete clinician-issued clinical records
Doctor → cannot silently delete finalized clinical documents
```

If deletion is required:

* authorize explicitly
* preserve metadata/audit information
* delete safely from storage
* consider retention requirements

---

# 35. Soft Delete / Status

A metadata state can be used:

```text
active
archived
deleted
```

where appropriate.

Do not implement a status simply because it sounds useful; follow actual retention requirements.

---

# 36. No Automatic Retention Deletion

Do not automatically delete documents after:

```text
30 days
1 year
5 years
```

without a verified retention policy.

Healthcare retention requirements should be explicitly defined before automated deletion.

---

# 37. Document Replacement

Do not silently replace an existing clinical document.

Bad:

```text
Upload corrected report
→ overwrite old storage object
```

Good:

```text
Original document
      ↓
New document/version
```

if versioning is required.

Historical clinical evidence should remain understandable.

---

# 38. Duplicate Documents

Do not aggressively deduplicate files based only on filename.

These may all legitimately exist:

```text
report.pdf
report (1).pdf
report-final.pdf
```

If deduplication is introduced, use content hashing plus explicit product rules.

---

# 39. File Integrity

Where practical, record:

```text
checksum/hash
```

for uploaded files.

This can help with:

* integrity verification
* duplicate detection
* debugging

Do not expose hashes unnecessarily to patients.

---

# 40. Virus / Malware Scanning

If infrastructure supports malware scanning, design the system to accommodate:

```text
uploaded
→ scanning
→ safe
```

or:

```text
uploaded
→ rejected
```

Do not claim that files are malware-free without an actual scanning mechanism.

If scanning is unavailable in this phase, document the limitation.

---

# 41. Untrusted Files

Treat all uploaded files as untrusted.

Never:

* execute them
* interpret them as application code
* render arbitrary HTML
* include them in server-side templates
* trust metadata blindly

---

# 42. Image Handling

Uploaded images may contain:

* EXIF metadata
* location metadata
* device information

If image processing is implemented, consider stripping unnecessary metadata.

Do not modify clinical evidence in a way that changes its meaning.

# 56. RLS

Implement database RLS for `patient_documents`.

The database must enforce ownership/resource isolation.

At minimum test:

```text
Patient A → Document A = ALLOW
Patient A → Document B = DENY
Doctor authorized for A → Document A = ALLOW
Unauthorized doctor → Document A = DENY
Receptionist → Document A = DENY
```

---

# 57. Storage Policies

Storage access must also be protected.

Do not rely only on database RLS.

The Storage object policy must correspond to the application's ownership/authorization architecture.

---

# 58. Storage Path and RLS Alignment

The storage path should make it possible to enforce secure policies.

For example:

```text
patients/{patientId}/documents/{documentId}/...
```

Then verify that:

```text
storage object patientId
=
authorized patient
```

where appropriate.

Do not blindly parse user-controlled paths.

---

# 59. Service Role

The Supabase service-role key may be used only in trusted server environments where absolutely necessary.

Never expose it to:

* browser
* client bundle
* public API response
* logs

---

# 60. Signed URL Endpoint

If using a server endpoint:

```text
GET /api/documents/:id/access
```

it must:

1. authenticate
2. authorize
3. verify document state
4. generate short-lived signed URL
5. return only the required information

Never accept arbitrary:

```text
storagePath
```

from the client and sign it blindly.

---

# 61. Path Traversal

Reject or safely handle:

```text
../
../../
absolute paths
unexpected bucket names
```

The server should generate storage paths rather than trusting client paths.

---

# 62. Document IDs

Use opaque identifiers.

Do not expose sequential IDs where avoidable.

Even with opaque IDs, authorization remains mandatory.

# 63. Access Logging

