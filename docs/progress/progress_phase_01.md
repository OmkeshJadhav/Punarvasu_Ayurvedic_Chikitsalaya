Status:

Summary:
Converted the Phase 00 architecture into a working application foundation:
`src/` layout, typed and validated configuration with a hard server/client

structured logging with redaction, schema validation at trust boundaries, the

### Implemented

**Structure**

* Migrated the App Router to `src/app/` with `git mv` (history preserved) and
  re-mapped `@/*` to `./src/*`.
* Enabled `noUncheckedIndexedAccess` and `noImplicitOverride` in `tsconfig`.
* Deleted the Next.js and Vercel marketing SVGs from `public/`.

**Configuration**

* `src/config/env.public.ts` — browser-safe values, validated with Zod.
  Validation is per consumer (`getSiteConfig`, `getSupabasePublicConfig`) so a
  page that needs only the site URL does not fail on unrelated configuration.
* `src/config/env.server.ts` — server-only values, fenced with `server-only`.
  The service-role key is reachable only via `requireSupabaseServiceRoleKey()`.
* `src/config/env-issues.ts` — formats problems as `NAME: reason`, never values.
* `src/instrumentation.ts` — full configuration check when the server boots,
  logging every missing or malformed variable by name.

**Supabase**

* `lib/supabase/browser.ts` — anon key, RLS-governed, browser only.
* `lib/supabase/server.ts` — per-request, cookie-bound, acts as the user.
* `lib/supabase/admin.ts` — service-role, `server-only`, session persistence
  disabled, documented usage rules.
* `src/types/database.ts` — generated-type placeholder for an empty schema,
  regenerated by `npm run db:types`.

**Errors, logging, validation, API**

* `lib/errors/` — `AppError` with seven categories, status and safe-copy maps,
  `ConfigurationError`, and `toAppError` so an unknown throw can never become a
  user-facing message.
* `lib/logging/` — JSON logger with levels, child loggers for correlation, and
  redaction of credential, contact and clinical keys with depth/length bounds.
* `lib/validation/` — `parseInput` (throws a `validation` `AppError` with field
  errors) plus shared `uuid`, `email`, `phone` and `requiredText` primitives.
* `lib/api/` — `x-request-id` correlation, the `{ ok, data }` / `{ ok, error }`
  envelope, and `createRouteHandler`, which supplies the id, logs failures and
  sanitizes the response.

**Application shell**

* Root layout with Punarvasu metadata, `metadataBase`, viewport and one font.
* `loading.tsx`, `error.tsx`, `global-error.tsx`, `not-found.tsx`, and a shared
  `StatusMessage` component used by the error and not-found screens.
* `globals.css` — neutral foundation tokens and a `prefers-reduced-motion` rule.
* `GET /api/health` returning `{ ok: true, data: { status: "ok" } }`.

**Tooling**

* Vitest (`vitest.config.mts`), Prettier with the Tailwind class-sorting plugin,
  and scripts for tests, formatting, migrations, type generation and the client
  bundle secret scan.

### Architectural decisions

1. **`src/` migration performed first**, as Phase 00 assigned. Done with
   `git mv` so history follows the files.
2. **Configuration is validated per consumer, not globally at import time.**
   A global check at module load would make every build and every page depend
   on configuration for capabilities it does not use. The startup check in
   `instrumentation.ts` still reports the complete picture.
3. **`instrumentation.ts` reports rather than throws.** A server that can still
   serve public pages plus a loud log line beats a crash loop, and every
   consumer of missing configuration fails safely on its own — a generic
   internal error, never a partial or unauthenticated result.
4. **`NEXT_PUBLIC_SITE_URL` defaults to `http://localhost:3000`** so the app
   runs with no configuration; the startup check flags a *production* instance
   that has not set it.
5. **`server-only` is the enforcement mechanism** for the server/client secret
   boundary, not a naming convention. Verified by deliberately importing
   `env.server.ts` from a client component: the build failed. Reverted.
6. **One error vocabulary (`AppError`).** The user-facing message and the
   diagnostic cause are separate fields, so leaking internals requires
   deliberate effort rather than a moment of inattention.
7. **The health endpoint uses the standard response envelope** rather than a
   bare `{"status":"ok"}`, so clients and monitors parse one shape everywhere.
   It reports no version, environment or dependency state.
8. **No CSP yet.** A policy written before the application loads any scripts,
   styles or third parties would be broken or decorative. Recorded in
   `SECURITY.md` §20 with the reason, assigned to the design/analytics phase.
9. **No authentication middleware yet.** `@supabase/ssr` session refresh belongs
   with the authentication phase; there are no sessions to refresh.
10. **Markdown is excluded from Prettier.** Reformatting ~10,000 lines of
    authored documentation would bury real changes in noise.

### Database Changes

No schema, no tables, no migrations — consistent with the phase scope.

Established:

* `supabase/config.toml` (Supabase CLI, pinned as a dev dependency)
* `supabase/migrations/` and the documented workflow in `supabase/README.md`
* `npm run db:migration`, `db:push`, `db:types`
* The rule that a table's RLS policies belong to the migration that creates it

Local auth defaults in `config.toml` were tightened from the CLI defaults:
minimum password length 6 -> 10, email confirmation enabled, secure password
change enabled, and the site URL aligned to `http://localhost:3000`. These
govern the local stack only; production settings live in the Supabase project
and are revisited by the authentication phase.

### Security Changes

* Server-only configuration boundary enforced by `server-only` (verified).
* Service-role key isolated behind a single accessor used by one module.
* Baseline security headers on every response; `X-Powered-By` disabled.
* Internal errors sanitized before reaching a client; correlation id returned
  instead of detail.
* Structured logs with redaction of credentials, contact details and clinical
  fields, plus depth and length bounds.
* Route-handler wrapper that logs unexpected failures and returns a safe body.
* `npm run security:scan-bundle` gate for server-only names and values in
  browser-downloadable output.
* Request correlation ids from callers are accepted only in a bounded, opaque
  format, so a header cannot poison the logs.

Negative controls (both confirmed the check actually works):

* Planting a known bundle string as a server-secret value made the bundle scan
  exit 1 and name the file.
* Importing `src/config/env.server.ts` from a `"use client"` component failed
  `next build` with *"'server-only' cannot be imported from a Client Component
  module"*. The probe was removed and the build re-run clean.

`npm run typecheck` runs `next typegen && tsc --noEmit`. Next.js 16 generates
the route and layout types (`LayoutProps`, `PageProps`) into `.next/types`, so
type checking a clean checkout fails without the typegen step. This matters for
CI, which starts from a clean tree.

Manual verification against `npx next start` and `npx next dev`:

* `next dev` starts, compiles and serves `/` and `/api/health` (both 200).

* `GET /api/health` -> `200 {"ok":true,"data":{"status":"ok"}}`, with
  `x-request-id` present.
* A well-formed upstream `x-request-id` is echoed; a malformed one is replaced.
* `POST /api/health` -> `405`.
* `/` -> 200, title `Punarvasu — Ayurvedic Clinic`.
* Unknown path -> 404 with the not-found page and `noindex`.
* Response headers confirmed: `X-Content-Type-Options`, `X-Frame-Options`,
  `Referrer-Policy`, `Permissions-Policy`, `X-DNS-Prefetch-Control`; no
  `X-Powered-By`.
* Startup log on a machine with no Supabase configuration:
  `{"timestamp":"...","level":"error","event":"startup.configuration_invalid","problems":["NEXT_PUBLIC_SUPABASE_URL: ...","NEXT_PUBLIC_SUPABASE_ANON_KEY: ..."]}`
  — names only, no values. This is the intended behaviour, not a defect.

Not verified, and not claimed:

* Any live Supabase operation. No Supabase project is configured in this
  environment, so the clients are exercised by type checking and build only,
  never against a real database. First real use is the authentication phase.
* `npx supabase start` / `db reset`. Both need Docker, which was not run here.
* Visual/responsive/accessibility review of the shell beyond semantic markup,
  keyboard-focusable controls and a reduced-motion rule. The UI is a technical
  placeholder; Phase 02 owns the design review.

### Risks discovered

| Risk | Severity | Disposition |
| --- | --- | --- |
| Supabase clients have never run against a real project | Medium | Unavoidable here: no project exists. First real exercise is the authentication phase, which must treat the integration as unproven. |
| No Content-Security-Policy | Medium | Deliberate and documented. Must not be forgotten when scripts and third parties arrive. |
| No middleware, so `@supabase/ssr` session refresh is absent | Medium | Correct for now (no sessions). The authentication phase must add it, or sessions will expire mid-use. |
| Log redaction is a key-name deny-list | Medium | A sensitive value under an unexpected key still gets logged. Policy remains "log identifiers, not content"; the list is reviewed as the domain grows. |
| `phase_02.md`–`phase_20.md` are still zero-byte | High for planning | Unchanged from Phase 00. Scope beyond Phase 01 is unspecified. |
| No CI pipeline | Medium | The gates exist as scripts but nothing enforces them on a push. |
| `@types/node` raised to v22 | Low | Matches the Node 22 runtime and Vitest 5's requirement; typecheck and build pass. |
| Local Supabase auth defaults hardened ahead of the auth phase | Low | Local stack only; the authentication phase should confirm them against the production project settings. |
